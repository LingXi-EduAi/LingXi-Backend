## 三、统一技术路线

```text
登录/鉴权
  -> AuthorizationInterceptor 解析 Token
  -> Controller 校验角色与资源所有权
  -> Service 校验状态机、幂等键和业务规则
  -> Mapper 写入任务/会话/消息/证据/日志
  -> AiTaskExecutionService 调用 AiAgentRouter + DifyGateway
  -> DifyEventAdapter 转换为 LingXiEvent v1
  -> TaskEventBroadcaster 推送 SSE（心跳、序号、断点恢复）
  -> AiTaskResultPersistenceService 持久化答案、引用和错误
  -> AiModelCallLogService 记录 usage、耗时、成本和失败原因
```

### 3.1 跨仓库契约顺序

1. 先在 `LingXi-Docs/interfaces` 登记 API、事件和迁移影响。
2. 后端先冻结 DTO、错误码、状态和数据库字段。
3. 代码实现必须包含单测；涉及 Dify 的路径使用 Mock Gateway。
4. 算法组提供真实 Chatflow/Workflow 载荷后，再补字段映射联调。
5. 前端按后端提交号接入，QA 固定前后端提交号回归。
6. 变更完成后更新任务卡、接口矩阵、测试证据和交接记录。

### 3.2 通用实现约束

- 所有受保护接口从当前登录用户推导 userId，禁止信任前端传入的所有权字段。
- Dify API Key、Token、用户凭据只从后端环境变量或配置中心读取，不写入日志和响应。
- SSE 事件必须有稳定事件类型、任务/子任务 ID、序号和可诊断错误码。
- 写入消息、证据和模型日志必须具备幂等策略，重复事件不能产生重复数据。
- 新 AI 链路优先；旧兼容接口只按明确任务维护，不新增业务功能。

## 四、按依赖顺序实施

### 波次 0：基线和契约（BE-01、BE-02）

**BE-01：`Conversation.version` 类型修复**

- 检查 `Conversation.version`、`lx_conversation.version` 及 MyBatis 映射。
- 新增迁移 `up/down/verify`，只修改对话表，不批量修改其他业务表。
- 处理已有 varchar 数据：迁移前验证均可转换为整数；异常值必须先记录并阻断迁移。
- 验收：数据库字段为整数、Java 类型为 `Integer`、迁移可回滚、编译和测试通过。

**BE-02：登录踢旧 Token**

- 定位 `TokenController` 登录流程，按 userId 查询既有 Token，再使旧 Token 失效。
- 保留新 Token 的生成和返回逻辑，避免误删刚生成的 Token。
- 测试连续登录：旧 Token 调用 `@Login` 接口返回 401，新 Token 正常返回 200。

### 波次 1：代码卫生（BE-03）

- 删除 `domain/test.java`、`RedisTestController`、`WebMvcConfig`、`FileDownLoad` 前先执行全仓引用搜索。
- 从 `MD5` 删除 `main()` 测试入口但保留被业务调用的工具方法。
- 将 `AiTaskExceptionHandler` 移入 `com.lxe.lx.exception`，同步包声明、扫描路径和测试引用。
- 验收：`mvn clean compile` 与 `mvn test` 通过，生产端点不再暴露测试接口。

### 波次 2：AI 主链路（BE-04、BE-05）

**BE-04：真实任务分解与执行**

- 先写失败测试，锁定复杂 query 至少产生 2 条子任务、包含依赖关系和真实 subtaskId。
- 在 `createTask` 中生成子任务及 `dependencyJson`；简单规则可按“计算/证明/检查/总结”等意图拆分，后续可替换为 Dify 调度结果。
- 执行器按依赖拓扑调度：无依赖任务可并行，有依赖任务必须等待前置成功；失败只阻断受影响分支。
- `TASK_DECOMPOSED`、`AGENT_ASSIGNED` 事件携带真实 subtaskId、agentType、executionNo。
- 验收：多子任务落库、事件顺序正确、重复执行幂等、停止和重试不破坏依赖图。

**BE-05：学科 Agent 路由**

- 等待算法组提供“学科名 → Dify 应用标识”清单，优先配置化读取。
- 关键词建议：数学/几何/代数，物理，化学；匹配顺序和默认应用写入配置说明。
- 空 query、未知学科、配置缺失统一回退 `CHATFLOW`，不能因路由失败阻断提问。
- 测试命中、未知、空值和配置缺失四类分支，并保留联调证据。

### 波次 3：业务闭环（BE-06、BE-07、BE-08）

**BE-06：AI 批改闭环**

- 确认 `HomeworkSubmission` 的 grade/comment/status 字段和教师手动批改接口契约。
- 新增 `AiGradingService`，输入学生作答、评分标准和提交 ID，调用 Dify Workflow。
- 使用现有 AI 执行器或 `@Async` 异步执行；成功后以提交 ID 幂等写回 grade/comment，并记录事件与模型日志。
- `ai.grading.enabled=false` 时不调用 Dify，状态保持 submitted，教师仍可手动批改。
- 覆盖成功、Workflow 失败、重复触发、关闭配置和权限校验测试。

**BE-07：演示种子数据**

- 创建 `sql/seed/demo_ai_data.sql`，引用真实用户、会话和班级外键。
- 至少写入 5 条任务、50 条事件、10 条证据、12 条模型调用日志，包含成功/失败/运行中状态。
- 使用固定主键并保证可重复执行；第二次执行不能报错或重复膨胀。
- 验收：MySQL 连续执行两次，日志页、学情页和回放页均能展示数据。

**BE-08：教师班级/学生用量聚合**

- 先校验教师对班级的管理权限，再查询班内学生和模型调用日志。
- 返回学生维度的调用次数、token、耗时、成本、失败数；空班级返回空数组。
- 聚合逻辑优先在 SQL 完成分组，Service 负责权限、DTO 和空值归一化。
- 测试多学生、多日志、无日志和跨班级访问拒绝。

### 波次 4：恢复与发布（BE-09 + 全量收尾）

**BE-09：任务恢复策略**

- 3 天工期内采用“中断标记”降级：启动时将 RUNNING 任务标记为可诊断的失败/中断状态，不声称自动续跑。
- 事件 message 统一为“后端重启，任务中断（可重新提问）”，并在职责文档中说明。
- 测试有任务、无任务、重复启动和异常数据四种情况均不抛异常。
- 后续若要真实续跑，另立 ADR 和任务，不在本路线中隐式扩大范围。

## 五、提交、联调和沟通规则

- 每个 BE 任务单独提交，提交信息使用 `feat(be-04): ...`、`fix(be-02): ...`、`test(be-06): ...` 格式。
- 一个任务至少包含：代码、测试、迁移/配置、文档和验收证据；未完成不得标记完成。
- BE-05/06/07/08 完成后，在协作群明确通知“接口/数据已可用”，附提交号和调用示例。
- 跨仓库联调必须同时记录后端提交号、前端提交号、Dify 配置版本和 QA 结果。
- 发现外部依赖阻塞时，标记“待外部输入”，写清缺失的 Dify 样例、字段或环境，不以代码提交掩盖阻塞。
