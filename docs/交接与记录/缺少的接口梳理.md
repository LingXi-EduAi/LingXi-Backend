# 缺少的接口梳理

更新时间：2026-09-05

## 先给结论

当前前端与后端的 AI 任务接口基本已经对齐，继续推进的主要问题不是再增加一个“转发接口”，而是冻结后端与 Dify 之间的输入、事件和文件协议。

当前真正需要算法/Dify 同学确认的内容有 5 项：

1. Chatflow 和 Workflow 的真实应用地址、应用类型及对应 API Key 是否分别配置。
2. Workflow 的 `inputs` 字段，特别是 `doc` 的真实类型和文件传递方式。
3. Chatflow/Workflow 实际 streaming 事件样例，以及最终结果、检索引用和 usage 的字段位置。
4. Dify 停止接口使用的外部 ID（`task_id` 还是 `workflow_run_id`）和失败/超时语义。
5. 一个本地任务是否只调用一次 Dify，还是要按 `ai_subtask` 逐个调用多个 Agent。

在以上内容确认前，不建议继续猜测 Dify 字段或新增重复接口。

## 一、当前链路

```text
前端
  │ token Header
  ▼
后端 /api/ai/tasks
  │ 创建 ai_task、ai_subtask
  ▼
DifyGateway
  ├─ Chatflow：POST {DIFY_CHATFLOW_BASE_URL}/chat-messages
  └─ Workflow：POST {DIFY_WORKFLOW_BASE_URL}/workflows/run
  │ streaming SSE
  ▼
DifyEventAdapter → ai_event/ai_message/ai_evidence/ai_model_call_log
  │
  ▼
前端 GET /api/ai/tasks/{taskId}/events（SSE，支持 Last-Event-ID）
```

Dify 的 `BASE_URL` 应填写到版本根路径（例如 `http://120.26.144.127:6004/v1`），代码会在其后追加 `/chat-messages`、`/workflows/run` 等路径；不要把完整接口路径再次写入 `.env`。

## 二、前端可使用的后端接口

所有新 AI 接口均使用请求头：

```http
token: <灵犀登录 Token>
```

统一响应结构为：

```json
{
  "status": 200,
  "msg": "success",
  "requestId": "后端生成的请求号",
  "data": {}
}
```

### 1. 任务主链路（已实现）

| 方法 | 路径 | 请求/用途 | 状态 |
|---|---|---|---|
| POST | `/api/ai/tasks` | 创建任务。Chatflow 至少传 `taskType=CHATFLOW, query`；Workflow 至少传 `taskType=WORKFLOW, inputs`；可传 `conversationId` | 已实现 |
| GET | `/api/ai/tasks/{taskId}` | 查询任务、子任务、结果和当前状态 | 已实现 |
| GET | `/api/ai/tasks/{taskId}/events` | 订阅 SSE；重连时传 `Last-Event-ID: {taskId}:{sequence}` | 已实现 |
| POST | `/api/ai/tasks/{taskId}/stop` | 停止当前用户的运行中任务 | 已实现 |
| POST | `/api/ai/tasks/{taskId}/subtasks/{subtaskId}/retry` | 重试满足依赖且失败的子任务 | 已实现，但需确认子任务真实执行范围 |

创建任务示例：

```json
{
  "taskType": "CHATFLOW",
  "query": "请总结这份材料",
  "inputs": {},
  "conversationId": ""
}
```

Workflow 示例：

```json
{
  "taskType": "WORKFLOW",
  "inputs": {
    "doc": {
      "transfer_method": "remote_url",
      "url": "https://可被 Dify 访问的公网地址/test.pdf",
      "type": "document"
    },
    "plan": "根据文档生成教学设计"
  }
}
```

SSE 每帧的 `data` 是 `LingXiEvent`：

```json
{
  "eventId": "任务ID:序号",
  "sequence": 3,
  "eventType": "ANSWER_DELTA",
  "taskId": "本地任务ID",
  "conversationId": "本地会话ID或 Dify 会话ID",
  "occurredAt": "2026-09-05T12:00:00Z",
  "status": "RUNNING",
  "payloadVersion": 1,
  "payload": {}
}
```

### 2. 会话和附件（已实现，但附件语义需确认）

| 方法 | 路径 | 说明 | 状态 |
|---|---|---|---|
| GET | `/api/ai/conversations` | 当前用户会话分页 | 已实现 |
| GET | `/api/ai/conversations/{conversationId}/messages` | 当前用户消息历史 | 已实现 |
| PATCH | `/api/ai/conversations/{conversationId}` | 重命名，Body 为 `{ "title": "..." }` | 已实现 |
| DELETE | `/api/ai/conversations/{conversationId}` | 软删除会话 | 已实现 |
| POST | `/api/ai/conversations/{conversationId}/continue` | 继续会话并返回 SSE | 已实现 |
| POST | `/api/ai/upload` | 本地文件上传，返回本地 `fileId/url` | 已实现 |

注意：`/api/ai/upload` 保存的是后端本地文件，不是 Dify 文件 ID。前端把它返回的 `fileId` 放入任务 `inputs`，当前任务执行器不会自动把该文件再上传到 Dify，也不会自动转换成 Dify 的 `document` 对象。

## 三、后端当前已经调用的 Dify 接口

### Chatflow

配置：`DIFY_CHATFLOW_BASE_URL`、`DIFY_CHATFLOW_API_KEY`。

| Dify 方法 | 路径（相对 BASE_URL） | 用途 | 请求要点 |
|---|---|---|---|
| POST | `/chat-messages` | 阻塞调用（旧兼容接口） | `query`、`inputs`、`conversation_id`、`user`、`response_mode=blocking` |
| POST | `/chat-messages` | 流式调用（新任务主链路） | 同上，`response_mode=streaming` |
| POST | `/chat-messages/{task_id}/stop` | 停止 Chatflow | Body `{ "user": "..." }` |
| GET | `/messages` | 查询 Dify 消息 | `user`、`conversation_id`、`limit`、可选 `first_id` |
| GET | `/conversations` | 查询 Dify 会话 | `user`、`limit`、`sort_by`、可选 `last_id` |
| POST | `/conversations/{conversation_id}/name` | 重命名 | `name/auto_generate`、`user` |
| DELETE | `/conversations/{conversation_id}` | 删除 | Body `{ "user": "..." }` |
| POST | `/files/upload` | 上传到 Dify | 仅 Gateway 已实现，当前 `/api/ai/upload` 未接入此方法 |

### Workflow

配置：`DIFY_WORKFLOW_BASE_URL`、`DIFY_WORKFLOW_API_KEY`。

| Dify 方法 | 路径 | 用途 | 请求要点 |
|---|---|---|---|
| POST | `/workflows/run` | 阻塞调用（旧兼容接口及批改服务） | `inputs`、`user`、`response_mode=blocking` |
| POST | `/workflows/run` | 流式调用（新任务主链路） | `inputs`、`user`、`response_mode=streaming` |
| POST | `/workflows/tasks/{task_id}/stop` | 停止 Workflow | Body `{ "user": "..." }` |

所有 Dify 请求均由后端附加 `Authorization: Bearer <API_KEY>`；前端不能也不应携带 Dify API Key。

## 四、目前缺少或需要冻结的交接接口/协议

### 1. 文件上传到 Dify 的正式链路（高优先级）

现在存在两条容易混淆的路径：

- 旧 `/api/filesUpload`：调用旧版 Dify 应用的 `/files/upload`。
- 新 `/api/ai/upload`：只保存本地文件，返回本地地址。

需要算法和前端确认一种方案：

1. 前端直接把公网 URL 作为 Workflow `remote_url` 传入；或
2. 后端新增“上传到指定 Chatflow/Workflow Dify 应用”的接口，返回 Dify `upload_file_id`，再由任务接口组装 `files`/`document`；或
3. Dify 应用接收本地后端可访问的 URL，并由后端负责生成稳定公网地址。

未确认前，不要把本地 `fileId` 当作 Dify `upload_file_id` 使用。

### 2. Workflow `doc` 输入协议（高优先级）

当前后端只校验 `inputs` 非空，然后原样转发。需要算法提供一份脱敏且可运行的真实 JSON，明确：

- 变量名是否固定为 `doc`；
- 类型是 `document`、字符串 URL，还是 Dify 文件 ID；
- `transfer_method` 可用值；
- 是否还需要 `plan`、用户信息或其他变量；
- 最大文件大小、格式和 URL 可访问要求。

### 3. Streaming 事件协议（高优先级）

当前适配器已处理：`message`、`agent_message`、`node_started`、`node_finished`、`message_end`、`workflow_finished`、`error`。

需要算法提供实际样例并确认是否还会出现：`workflow_started`、`node_exception`、`message_file`、`message_replace`、检索事件、迭代/并行节点事件、`ping`。未知事件目前会被忽略，不会进入 `ai_event` 或前端 SSE。

### 4. 终止和外部 ID 协议（中高优先级）

后端会从事件中的 `task_id` 或 `workflow_run_id` 保存 Dify 外部 ID，再调用停止接口。需要确认：

- Chatflow 停止使用哪个字段；
- Workflow 停止路径所需的 ID 是否就是事件中的 `task_id`；
- Dify 返回 404、409、429、5xx 时，分别应映射为停止失败、幂等成功还是可重试失败；
- 用户点击停止后，迟到的成功/失败事件必须保持本地 `STOPPED` 终态不被覆盖。

### 5. 子任务与 Agent 调用边界（高优先级）

当前代码会创建多个 `ai_subtask` 并写入分解/分配事件，但执行器首版只启动第一个子任务的一次 Dify 流。后续子任务的真正调用顺序、每个 Agent 对应的 Dify 应用、依赖完成条件需要算法确认。

如果 Dify Chatflow 自己负责完整编排，应把它视为一个 Dify 调用，不再要求后端逐子任务调用；如果后端负责编排，则需要补齐“子任务完成后启动下一个 Agent”的接口和状态规则。

### 6. 结果、证据和 usage 字段（中优先级）

当前后端按常见 Dify 结构读取：

- Chatflow：`answer`、`message_id`、`conversation_id`、`metadata.usage`；
- Workflow：`data.outputs`、`workflow_run_id/task_id`；
- 检索引用：`metadata.retriever_resources` 或 `data.retriever_resources/retrieval_resources`；
- 用量：`metadata.usage.total_tokens`、`total_price/total_cost/cost`，必要时读取 `data` 同名字段。

需要算法提供成功、失败、429、超时各一份脱敏响应，确认最终展示字段、模型名、Token、费用和币种是否符合上述路径。否则消息可以联调，但证据和模型调用统计只能算兼容性实现，不能算真实验收完成。

## 五、仍需环境侧确认的事项

1. 云 MySQL 已执行并验证 BE-11 的 `ai_conversation` 迁移。
2. 云端 Redis、后端实例和 Dify 网络连通性已验证。
3. 用真实登录 Token 完成一次：创建 Chatflow → SSE → 断线续传 → 任务快照 → 会话历史。
4. `DIFY_CHATFLOW_BASE_URL` 和 `DIFY_WORKFLOW_BASE_URL` 是否分别指向正确应用，不能只验证 TCP 端口。
5. 保证 Dify API Key 只存在后端 `.env`/部署环境，不进入前端、Apifox 公共文档或日志。

## 六、建议的交接回传格式

算法同学只需回传以下内容，后端即可继续做契约测试和最小改动：

```text
Chatflow 应用：BASE_URL、事件样例（message/message_end/error）、最终答案字段、usage 字段
Workflow 应用：BASE_URL、inputs 完整样例（尤其 doc）、workflow_finished 样例、失败样例
文件方案：remote_url / Dify upload_file_id / 其他
停止方案：Chatflow 与 Workflow 各自使用的外部 task ID 字段
编排边界：Dify 自己编排，还是后端按 ai_subtask 逐个调用
```

收到这些确认后，后端下一步只需要补充对应字段映射、契约测试和必要的文件转发，不需要再设计一套新的前端接口。
