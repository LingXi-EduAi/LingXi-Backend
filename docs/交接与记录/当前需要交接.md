## 当前技术阻塞（先看这里）

后端 BE-01～BE-09 已完成。按照任务书继续开发时，必须先确认或拿到真实数据才能定型的技术问题只有以下几类：

1. **BE-10-3 的证据字段映射**：必须拿到一次真实的 Dify 检索/引用 SSE，才能确定 `ai_evidence` 各字段从哪里读取。用户问题和最终回答的消息持久化不受此项阻塞。

2. **附件是否属于本阶段范围以及如何落库**：如果本阶段必须持久化附件，现有 `ai_message` 没有附件字段，必须在“增加 JSON 字段、增加附件表、暂不持久化”中确定一种；如果任务书本阶段不要求附件，则不构成阻塞。

3. **BE-11-2 的会话持久化模型**：新 AI 任务链路只写 `ai_task.conversation_id`，但重命名和软删除需要标题、删除状态；旧 `lx_conversation` 又不会随新 AI 任务创建。必须确定复用并补齐旧表，还是新增 `ai_conversation`。

4. **BE-14-2 的限流参数**：任务卡规定 Redis、按用户、429 和 `Retry-After`，但没有规定时间窗口、请求上限和是否区分接口，无法确定最终配置默认值。

5. **BE-14-3 的数据保留与擦除规则**：必须确定保留天数、删除涉及哪些 AI 表、审计日志是否保留，以及数据库记录采用软删除还是物理删除。

以下内容不是编码硬阻塞：

1. BE-10-1、BE-10-2、BE-13-1 可直接按任务卡实施。
2. BE-13-2 已在任务卡中明确 Chatflow/Workflow 的 usage 路径和模型名缺失时的记录方式，可先实现，再用真实事件验收。
3. 会话接口的分页、排序和响应结构可由后端先给出保守契约，前端只需在联调前确认，不应阻塞 Mapper 和 Service 开发。
4. MySQL、Redis、Dify、Nginx 和后端进程属于运行验收条件，不是需求或代码设计阻塞。

## 3. BE-11 技术阻塞

### 3.1 会话模型缺口

1. `ai_task.conversation_id` 可分组和校验用户，但没有标题、删除状态和独立版本。
2. `lx_conversation` 不会由新任务自动创建，没有适合的新 AI 会话标题字段。
3. `lx_conversation.version` 数据库类型和 Java 类型不一致。
4. Dify conversation ID 是外部标识，不能作为灵犀业务主键。

必须确认：

| 编号 | 技术确认 |
| --- | --- |
| ARCH-01 | 是否新增独立 `ai_conversation` 表 |
| ARCH-02 | 若不新增表，标题和软删除状态存在哪里 |
| ARCH-03 | 首次任务何时创建会话记录 |
| ARCH-04 | Dify conversation ID 何时同步到本地 |
| ARCH-05 | 已有 `ai_task` 如何回填会话 |

这个问题不解决，BE-11 只能查询，无法正确实现重命名和软删除。

### 3.2 前端需要冻结的接口

| 编号 | 技术确认 |
| --- | --- |
| FE-06 | 会话列表返回字段和 JSON 示例 |
| FE-07 | 消息返回字段及证据嵌套方式 |
| FE-08 | 页码或游标分页 |
| FE-09 | 首屏返回最早消息还是最近消息 |
| FE-10 | PATCH 字段和标题长度 |
| FE-11 | DELETE 后是否隐藏、是否允许恢复 |
| FE-12 | 继续对话传本地 ID 还是 Dify ID |

建议前端只传灵犀本地 `conversationId`，由后端管理 Dify ID。

### 3.3 删除与继续对话冲突

任务卡同时出现软删除、级联物理删除，以及继续调用旧 `/api/ai/task/stream`。

保守技术方案：

1. 仅本地软删除。
2. 不删除任务、事件、消息和 Dify 远端数据。
3. 继续对话统一使用新 `POST /api/ai/tasks`。
4. 跨用户和已删除会话统一返回 404。
