## 二、已完成能力

### 1. Dify 中转与安全配置

- Dify 调用统一经过 `DifyGateway`，前端不接触 Dify API Key。
- Chatflow 和 Workflow 使用独立的 `.env` 配置：

```properties
DIFY_CHATFLOW_BASE_URL=<chatflow-base-url>/v1
DIFY_CHATFLOW_API_KEY=<chatflow-api-key>
DIFY_WORKFLOW_BASE_URL=<workflow-base-url>/v1
DIFY_WORKFLOW_API_KEY=<workflow-api-key>
```

- 数据库、Redis、短信服务和 Dify 密钥均不应写入源码或提交到 Git。
- 修改 `.env` 后必须重启后端。
- 仓库只能证明敏感配置已改为环境变量，不能证明线上旧凭据已经失效；接手时应向项目负责人确认数据库、Dify 和云服务密钥是否完成轮换。

### 2. 登录、用户映射和权限

- 所有需要登录的接口使用请求头：

```http
token: <灵犀登录接口返回的 Token>
```

- 后端从 Redis Token 中读取当前用户 ID，并将其作为 Dify `user`。
- 学生测试账号：`student114514 / 123456`
- 教师测试账号：`teacher114514 / 123456`
- 任务、会话等资源不能仅依赖前端传入的用户 ID；后端会从登录上下文校验所有权。

## 三、当前可用 AI 接口

### 1. 创建持久化 AI 任务

```http
POST /api/ai/tasks
Content-Type: application/json
token: <登录 Token>
```

Chatflow 请求示例：

```json
{
  "taskType": "CHATFLOW",
  "query": "1+1等于多少？",
  "inputs": {},
  "conversationId": ""
}
```

Workflow 请求要求 `inputs` 非空；Workflow 的具体 `doc`、`plan` 等字段必须以算法同学最终发布的 Dify 输入定义为准。

成功响应使用新 AI 统一结构：

```json
{
  "status": 200,
  "msg": "success",
  "requestId": "...",
  "data": {
    "taskId": "灵犀本地任务ID",
    "conversationId": "灵犀本地会话ID",
    "status": "CREATED",
    "eventUrl": "/api/ai/tasks/{taskId}/events"
  }
}
```

### 2. 查询任务快照

```http
GET /api/ai/tasks/{taskId}
token: <登录 Token>
```

返回任务状态、进度、子任务、最终结果和错误信息。跨用户或不存在的任务统一返回 HTTP 404。

### 3. 订阅任务 SSE

```http
GET /api/ai/tasks/{taskId}/events
token: <登录 Token>
Accept: text/event-stream
Last-Event-ID: {taskId}:{sequence}
```

- 前端应使用 `fetch + ReadableStream`，不能依赖原生 `EventSource`，因为接口需要 Token Header。
- 事件先入库再广播。
- 缺少 `Last-Event-ID` 时从 sequence 0 开始；续传格式固定为 `{taskId}:{sequence}`。
- 事件协议见 [LingXiEvent协议-v1.md](../接口与协议/LingXiEvent协议-v1.md)。

### 4. 停止任务

```http
POST /api/ai/tasks/{taskId}/stop
token: <登录 Token>
```

- 只有当前用户可以停止自己的 `RUNNING` 任务。
- 重复停止已是 `STOPPED` 的任务幂等成功。
- 已成功、失败等其他终态再次停止返回 HTTP 409。

### 5. 重试失败子任务

```http
POST /api/ai/tasks/{taskId}/subtasks/{subtaskId}/retry
token: <登录 Token>
```

仅支持 Agent 类型 `CHATFLOW` 和 `WORKFLOW`；子任务必须为 `FAILED`、依赖已完成且未超过 `AI_SUBTASK_MAX_RETRIES`（默认 3 次）。

### 6. 兼容接口

以下旧接口继续保留，尚未迁移下线：

- `POST /api/chatflow/messages`
- `GET /api/chatflow/messages`
- `POST /api/workflow/run`
- `POST /api/ai/task`
- `POST /api/ai/task/stream`
- 旧的 `/conversation/**` 和其他教学业务接口

旧接口仍使用旧 `ResultConstant` 响应结构。新 `/api/ai/tasks/**` 缺 Token 时响应包含 `status`、`msg`、`requestId` 和 `data:null`。

### 2. Redis

- 登录 Token 和运行时连接状态依赖 Redis。
- 标准配置是 `REDIS_HOST`、`REDIS_PORT`、`REDIS_PASSWORD`、`REDIS_DATABASE`。
- 本机此前验证时 Windows 无法直接访问 WSL 的 `localhost:6379`，通过临时环境变量连接 WSL IP 的 `6380` 端口；这不是仓库默认配置。
- 接手部署时应优先确认后端进程能访问 Redis，再测试登录和 AI 接口。


```powershell
Invoke-WebRequest http://127.0.0.1:5678/ -UseBasicParsing
Invoke-WebRequest http://127.0.0.1:5678/test/get -UseBasicParsing
```

检查新 AI 鉴权契约：

```powershell
Invoke-WebRequest http://127.0.0.1:5678/api/ai/tasks/demo -UseBasicParsing -SkipHttpErrorCheck
```

预期为 HTTP 401，JSON 中包含：

```json
{
  "status": 401,
  "msg": "参数缺少 token 值",
  "requestId": "非空字符串",
  "data": null
}
```
